# polymarket_bot

Арбитражный бот для многоисходных (NegRisk) событий Polymarket:
покупка недооценённых No-позиций → Convert → pUSD/пакет Yes → (при
необходимости) продажа пакета. Управление полностью через Telegram.
Рассчитан на непрерывную работу на локальном компьютере, который
остаётся включённым - отказоустойчивость важнее новых фич.

**Текущий статус:** сбор данных и сканер арбитража - полностью рабочие
и протестированные. Реальное исполнение сделок написано и может быть
включено, но помечено местами как требующее проверки на реальном
аккаунте перед серьёзным размером (см. «Что проверить перед реальными
деньгами» ниже) - потому что некоторые детали (например, точный формат
ответа ордера CLOB) нельзя до конца проверить без живого API-ключа.

## Как это работает: механика коротко

В событии с несколькими взаимоисключающими исходами (выигрывает ровно
один) справедливо: `Yes_A + Yes_B + ... = $1`. Если из-за низкой
ликвидности это равенство нарушается - возникает арбитраж. Бот ищет два
вида возможностей:

- **convert_all** - купить No по ВСЕМ исходам события разом,
  сконвертировать одним вызовом контракта `convertPositions` → контракт
  отдаёт `(n-1) × amount` в pUSD **напрямую**, без остатка в виде
  Yes-токенов. Самый безопасный случай: после того как купили все ноги,
  продавать уже нечего.
- **convert_single** - купить No по одному исходу → Convert даёт пакет
  Yes-токенов по остальным исходам → эти Yes нужно **продать**, чтобы
  реализовать прибыль. Два рыночных действия подряд - риск выше
  (движение цены между покупкой и продажей, частичное исполнение).

Обе формулы проверены побайтово против реального, верифицированного
контракта `NegRiskAdapter` на PolygonScan (не просто по документации).
Подробный разбор с числовым примером был дан в чате раньше в этом
диалоге.

## Установка

```bash
python -m venv venv
venv\Scripts\activate          # на Windows; source venv/bin/activate на Linux/Mac
pip install -r requirements.txt
copy .env.example .env         # copy на Windows, cp на Linux/Mac
```

Без дополнительной настройки `.env` бот уже будет собирать данные и
искать возможности (сделок совершать не будет - для этого нужны
отдельные явные включения, см. ниже).

## Запуск

```bash
uvicorn app.main:app --app-dir backend --host 127.0.0.1 --port 8000
```

Статус:
```bash
curl http://127.0.0.1:8000/api/v1/health
```

В Windows PowerShell `curl` — это алиас на `Invoke-WebRequest` с другим
синтаксисом (флаг `-s` не работает, PowerShell начнёт интерактивно

```powershell
curl.exe http://127.0.0.1:8000/api/v1/health      # вызвать настоящий curl, а не алиас
Invoke-RestMethod http://127.0.0.1:8000/api/v1/health   # нативно, сразу разобранный JSON
```

### Непрерывная работа на локальном компьютере (Windows)

Поскольку компьютер остаётся включённым, а не арендуется как сервер,
есть два уровня защиты от падений:

**Уровень 1 - сам бот не падает молча.** Каждый фоновый цикл (сборщик,
сканер, исполнитель) оборачивает свою работу в `try/except` и продолжает
со следующей итерации, даже если текущая упала с ошибкой - ошибка
попадает в лог (`data/bot.log`, с ротацией) и в `/api/v1/health`, но сам
процесс не останавливается. Все обращения к внешним API/RPC делают
несколько попыток с задержкой (`tenacity`) на случай кратковременных
сетевых сбоев.

**Уровень 2 - перезапуск, если упал весь процесс** (например, Python
упал целиком, или Windows перезагрузился). Два варианта:

1. **Просто и быстро**: запустите `scripts\run_supervised.bat` - окно
   будет само перезапускать бота при падении. Минус: не переживает
   перезагрузку компьютера без повторного запуска вручную (можно
   положить ярлык в папку автозагрузки - `Win+R` → `shell:startup`).

2. **Надёжнее (рекомендуется)**: установите как службу Windows через
   `scripts\install_service.ps1` (нужен бесплатный NSSM, см. комментарии
   в скрипте). Служба стартует при загрузке компьютера ещё до входа в
   систему, сама перезапускается при падении, не привязана к открытой
   сессии.

**Дополнительно:** отключите спящий режим для компьютера, который
должен работать непрерывно - `Параметры → Система → Электропитание и
спящий режим → Никогда`, иначе Windows сама "поставит на паузу" бота.

## Управление через Telegram

1. Создайте бота через [@BotFather](https://t.me/BotFather), получите
   токен → `TELEGRAM_BOT_TOKEN` в `.env`.
2. Узнайте свой числовой Telegram ID (например, через
   [@userinfobot](https://t.me/userinfobot)) → `TELEGRAM_ADMIN_IDS` в
   `.env` (можно несколько через запятую). **Без этого бот отвечает
   всем "доступ запрещён"** - это единственная граница безопасности.
3. Команды: `/status` (статус процессов + живой баланс), `/opportunities`
   (последние найденные возможности), `/pause` (аварийный стоп
   исполнителя - сделки прекращаются немедленно, процесс продолжает
   работать), `/resume`.

## Настройка кошелька (нужно только для реальных сделок)

```env
WALLET_ADDRESS=0x...            # публичный адрес - для чтения баланса
WALLET_PRIVATE_KEY=0x...        # приватный ключ - ТОЛЬКО в .env, не в коде
WALLET_SIGNATURE_TYPE=0         # см. ниже
WALLET_FUNDER_ADDRESS=          # см. ниже
```

Если аккаунт на Polymarket заведён через **email/соцсети** (не через
MetaMask напрямую) - `WALLET_SIGNATURE_TYPE` почти наверняка не `0`, а
`WALLET_FUNDER_ADDRESS` должен быть адресом, который показывается в
профиле на polymarket.com (там реально лежат ваши средства), а не
обязательно тем же адресом, что выводится из `WALLET_PRIVATE_KEY`. Если
заводили через MetaMask напрямую - скорее всего `WALLET_SIGNATURE_TYPE=0`
и `WALLET_FUNDER_ADDRESS` можно оставить пустым.

**Разовая настройка перед первым Convert**: нужно разрешить контракту
NegRiskAdapter двигать ваши позиционные токены
(`NegRiskAdapterClient.build_set_approval_tx` в коде строит эту
транзакцию - отправить её один раз нужно вручную, автоматически при
первом запуске это не делается намеренно).

## Капитал: как бот начинает со $100 и растёт

Размер каждой сделки и дневной лимит считаются **долей от текущего
живого баланса pUSD на кошельке** (`EXECUTION_TRADE_FRACTION` /
`EXECUTION_DAILY_FRACTION`), а не от фиксированной суммы. Это и есть
накопление капитала: баланс вырос после удачных сделок → следующие
сделки автоматически крупнее; баланс просел → мельче. `STARTING_BANKROLL_USD=100`
используется только для справки и ни на что не влияет напрямую - реальный
размер всегда считается от того, что бот видит on-chain прямо сейчас.

Если баланс прочитать не удалось (RPC недоступен) - исполнитель
**полностью пропускает цикл**, а не торгует по угаданной цифре. Это
намеренное поведение, не баг.

Значения по умолчанию (`EXECUTION_TRADE_FRACTION=0.08`,
`EXECUTION_DAILY_FRACTION=0.30`) при балансе $100 дают ~$8 на сделку и
~$30 лимит в день - разумная отправная точка для «не хочу сильно
рисковать», можно уменьшить ещё, поправив эти доли в `.env`.

## Включение реального исполнения - два независимых переключателя

```env
ENABLE_ONCHAIN_EXECUTION=false   # общий рубильник подписи транзакций
RUN_EXECUTOR_IN_PROCESS=false    # запускать ли цикл исполнения вообще
```

Пока хотя бы один из двух - `false`, бот **только логирует возможности**
и шлёт их в Telegram, ничего не покупает. Включать оба стоит только
после того, как убедились на `/opportunities`, что сканер находит
разумные возможности на вашем рынке, и прочитали раздел ниже.

## Что проверить перед реальными деньгами

- **Выручка от продажи при convert_single не до конца подтверждена.**
  Код считает её по разнице баланса pUSD кошелька до/после продажи
  (надёжно), а не по полю ответа ордера CLOB (там нужно свериться с
  реальным аккаунтом, какое именно поле содержит сумму сделки - сделано
  максимально безопасно, но не проверено живым API-ключом).
- **Разрешение `setApprovalForAll`** нужно отправить вручную один раз
  (см. выше) - без него Convert будет падать с ошибкой on-chain.
- **Адреса контрактов** (`NEG_RISK_ADAPTER_ADDRESS`, `CTF_ADDRESS`,
  `PUSD_ADDRESS` в `config.py`) сверены по
  https://docs.polymarket.com/resources/contracts - стоит свериться
  ещё раз самостоятельно, это не то, во что нужно верить на слово.
- **Комиссия Convert** в сканере считается по точной формуле из
  контракта (`fee = amount × feeBips / FEE_DENOMINATOR`), но
  `getFeeBips` читается on-chain с запасным значением при недоступности
  RPC - проверьте, что `NEGRISK_FEE_BIPS_FALLBACK` разумен для ваших
  рынков, если RPC часто недоступен.
- **Augmented NegRisk-события** (с ещё не раскрытыми placeholder-
  исходами вроде «Other») сканер пропускает целиком - текущая логика не
  рассчитана на них.
- Остаются риски, перечисленные в самой стратегии: движение цены между
  сканированием и исполнением, частичное исполнение, проскальзывание,
  ошибка резолюции рынка. Сканер даёт оценку на момент сканирования, не
  гарантию результата исполнения.

## Восстановление после сбоя

Каждое исполнение проходит фазы (`execution_states` в БД): купили No →
сконвертировали → продали (если нужно) → готово. Если процесс упадёт
посреди этой последовательности, при следующем запуске `main.py` найдёт
незавершённую запись и **громко предупредит** (лог + Telegram), но не
будет пытаться доиграть её автоматически - решать, что делать с
зависшей позицией (докупить, продать как есть, оставить до резолюции),
должен человек. Это намеренно: автоматическое доигрывание прерванной
денежной операции рискованнее, чем пауза на ручное решение.

## Открытые решения

- **БД для долгой работы:** SQLite подходит для одного компьютера;
  Postgres - смена `DATABASE_URL`, код не меняется.
- **Telegram в отдельном процессе:** сейчас бот работает в одном
  процессе с остальным (проще для одного компьютера). Если понадобится
  разнести на отдельные процессы - архитектура уже к этому готова
  (каждый сервис запускается и как `python -m app.services.<модуль>`).

## Если сканер ничего не находит

```bash
python scripts/diagnose.py
```

Покажет: сколько NegRisk-событий собрано, у скольких из них есть ВСЕ
исходы с живым стаканом (условие, при котором сканер вообще способен
что-то посчитать), и список реальных текущих раскладов цен без фильтра
по минимальной прибыли — чтобы отличить «данных не хватает» от
«возможностей сейчас действительно нет».

Частая причина нулевого результата: `Collector` раньше собирал только
топ-N рынков по объёму глобально, а не по событиям — у события из 15+
исходов (выборы, премии и т.п.) в топ обычно попадали 2-3 самых
торгуемых, и сканеру не хватало данных по остальным, чтобы оценить
`convert_all`/`convert_single` целиком. Это исправлено: сборщик теперь
отдельно листает ВСЕ активные NegRisk-рынки через Gamma (`neg_risk=true`),
независимо от объёма, гарантируя полный набор исходов для каждого
события.

Если после этого диагностика показывает полные события, но ни одного
расклада выше `NEGRISK_MIN_PROFIT_PCT` — это, скорее всего, нормально:
на ликвидных 5-минутных крипторынках за расхождения выше 1% уже
конкурируют профессиональные маркет-мейкеры, закрывающие их за секунды.
Стоит попробовать менее ликвидные/длинные события (выборы, спорт,
премии) — там конкуренция ниже и расхождения держатся дольше.

### Если сбор стаканов идёт очень долго или кажется зависшим

При включении полного сбора NegRisk-рынков их может набраться тысяча и
больше (у многоисходных событий бывают десятки исходов с почти нулевым
объёмом). Две защиты от этого:

- `COLLECTOR_MAX_ORDERBOOK_TOKENS_PER_CYCLE` — жёсткий потолок на число
  токенов, по которым запрашивается стакан за один цикл. Применяется
  **на уровне события целиком**: все исходы одного NegRisk-события
  группируются и берутся/пропускаются вместе, приоритет — по суммарному
  объёму события. Событие никогда не разрезается пополам (иначе сканер
  не сможет оценить его целиком — ровно так когда-то появлялся баг «от
  события осталось geq 1 исход вместо всех»); то, что не поместилось,
  соберётся в одном из следующих циклов.
- `COLLECTOR_ORDERBOOK_PHASE_TIMEOUT_SECONDS` — вся фаза сбора стаканов
  обязана уложиться в этот таймаут; если нет, то, что успели собрать,
  всё равно сохраняется, а цикл не блокируется навсегда.

### Если бот замирает на часы без единой строки в логе

Это отдельная от предыдущей проблема: таймаут стоял только на фазу
сбора стаканов, а сбор метаданных (постраничные запросы к Gamma) был
защищён только внутренним таймаутом `httpx` - которого на практике не
всегда хватало. Добавлена многослойная защита: таймаут на каждый
отдельный запрос страницы к Gamma, и поверх него - жёсткий таймаут на
весь цикл сборщика целиком (`COLLECTOR_CYCLE_TIMEOUT_SECONDS=180`). Что
бы ни зависло внутри, дальше 2-3 минут цикл не может молчать - либо
завершится с тем, что успел собрать, либо явно напишет в лог, что
прервался по таймауту. Проверено тестом с полностью «подвешенным»
клиентом Gamma - раньше это блокировало бы процесс навсегда, теперь
обрывается за секунды.

### Найденная причина зависания «на 2000 рынках» (исправлено)

Дамп сторожевого таймера показал: главный поток стоял на синхронном
`web3`-запросе к публичному Polygon RPC (`get_fee_bips`), вызванном
прямо из сканера. Сканер запрашивал комиссию для **каждого** события:
пока в БД мало рынков - единицы запросов, при ~2000 рынках - сотни
блокирующих HTTPS-запросов подряд (с retry и `sleep`), и весь процесс,
включая FastAPI/health, замирал на часы. Исправлено:

- комиссия читается только для событий, где уже есть кандидат (она лишь
  уменьшает прибыль - отсев без неё безопасен), не более
  `NEGRISK_MAX_FEE_LOOKUPS_PER_CYCLE` за цикл, с кэшем;
- запрос идёт в потоке (`asyncio.to_thread`) под таймаутом, при сбое -
  запасное `NEGRISK_FEE_BIPS_FALLBACK`;
- у RPC-провайдера задан таймаут (`POLYGON_RPC_TIMEOUT_SECONDS`), клиент
  один общий (раньше каждый новый `Web3` ещё и дополнительно спрашивал
  `chain_id`);
- то же для баланса в `/health`, Telegram `/status` и исполнителе.

Проверено на 700 событиях с медленным RPC: пауза event loop ≤ ~120 мс
(`tests/`). Для постоянной работы всё же вставьте свой RPC-URL
(Alchemy/Infura/QuickNode) в `POLYGON_RPC_URL` - публичный лимитирует.

### Если бот снова замёрз целиком (и health не отвечает)

Это значит, что заблокирован сам event loop, а не отдельная задача -
таймауты на запросы тут не помогут. Для этого встроен сторожевой
таймер: если процесс не откликается дольше `HANG_WATCHDOG_TIMEOUT_SECONDS`
(по умолчанию 90с), в файл `data/bot_hang_dump.log` автоматически
записываются стек-трейсы **всех** потоков - видно точную строку кода,
на которой всё встало. Файл пуст, пока всё работает нормально.

Что сделать при следующем зависании:
1. Подождите ~2 минуты после того, как бот замолчал.
2. Откройте `data\bot_hang_dump.log` и пришлите его содержимое целиком.
3. Параллельно в Диспетчере задач посмотрите на `python.exe`: ~0% ЦП и
   нулевая нагрузка на диск - ждёт чего-то (блокировка/сеть); 100% одного
   ядра - зациклился вычислительно. Это тоже полезно сообщить.

Если на Windows зависание связано с диском, попробуйте добавить папку
проекта (`data\`) в исключения антивируса/Защитника Windows - он
сканирует каждую запись в файлы БД и умеет сильно тормозить SQLite.

### Если БД «зависает» при росте числа записей

Это была реальная проблема: SQLite блокирует файл целиком на время
записи, а при росте числа рынков транзакция апсерта становится длиннее
(дольше окно блокировки) — при этом `Collector`, `Scanner`, `Executor`
и Telegram-бот лезут в тот же файл параллельно как независимые
asyncio-задачи. Исправлено: включён WAL-режим SQLite (читатели не ждут
писателя) и `busy_timeout=10с` (при конфликте ждём и повторяем, а не
падаем сразу с «database is locked»). Проверено нагрузочным тестом:
запись 2000 рынков параллельно с читателем — 2.2с, без единой ошибки
блокировки.

Заодно добавлена чистка старых снепшотов стакана
(`COLLECTOR_SNAPSHOT_RETENTION_HOURS=24`, раз в
`COLLECTOR_PRUNE_EVERY_N_CYCLES=60` циклов) — таблица снепшотов
append-only и иначе растёт без ограничения, что через недели
непрерывной работы стало бы той же проблемой снова.

Если после этого всё ещё медленно — поднимите
`COLLECTOR_MAX_ORDERBOOK_TOKENS_PER_CYCLE` аккуратно либо смиритесь с
тем, что редкие низковолюмные события будут собираться не каждый цикл,
а через один-два — это нормально, свежесть в пределах пары минут не
критична.
